# Dealership Lot — Car Dealership Inventory System

A full-stack car dealership inventory system built as a TDD kata: a
Node.js/TypeScript/Express/SQLite REST API with JWT auth, and a React +
TypeScript + Tailwind single-page app on top of it.

```
car-dealership/
├── backend/     Express + TypeScript API, SQLite, Jest/Supertest tests
├── frontend/    React + TypeScript + Tailwind v4 SPA (Vite)
├── PROMPTS.md   Raw AI chat log used to build this project
└── README.md    You are here
```

## Design

Rather than a generic admin-panel look, the UI is grounded in the actual
subject — a car lot: charcoal/amber/racing-green palette, a condensed
display face (Oswald) that reads like dealership signage, and two signature
details lifted from a real car lot: each vehicle card carries a **window-
sticker price tag** and a **fuel-gauge-style stock indicator** instead of a
plain "Qty: N" label. Admin-only controls (Edit/Restock/Delete) are hidden
entirely for non-admin users, not just disabled.

## Setup & running locally

### Prerequisites
- Node.js **22.5+** (uses the built-in `node:sqlite` module — no native
  compiler/build toolchain required on any OS, unlike drivers such as
  `better-sqlite3` or `sqlite3` that need node-gyp)

### 1. Backend

```bash
cd backend
npm install
cp .env.example .env
npm run seed     # creates demo admin/customer + 8 sample vehicles
npm run dev       # starts the API on http://localhost:4000
```

Run the test suite:

```bash
npm test          # runs all 36 tests with coverage
```

### 2. Frontend

In a second terminal:

```bash
cd frontend
npm install
npm run dev        # starts the SPA on http://localhost:5173
```

The Vite dev server proxies `/api/*` requests to `http://localhost:4000`
(see `frontend/vite.config.ts`), so no CORS configuration is needed locally.
Open **http://localhost:5173** and log in with one of the demo accounts
above (or register a new customer account).

### 3. Production build

```bash
# Backend
cd backend && npm run build && npm start

# Frontend
cd frontend && npm run build   # outputs to frontend/dist/
```

## API Reference

All `/api/vehicles/*` routes require `Authorization: Bearer <token>`.
Delete and restock additionally require an `admin` role token.

| Method | Endpoint                        | Auth        | Description                          |
|--------|----------------------------------|-------------|---------------------------------------|
| POST   | `/api/auth/register`             | —           | Create a user (`role` defaults to `user`) |
| POST   | `/api/auth/login`                 | —           | Returns `{ token, user }`            |
| GET    | `/api/vehicles`                   | User        | List all vehicles                    |
| GET    | `/api/vehicles/search`            | User        | Query params: `make`, `model`, `category`, `minPrice`, `maxPrice` |
| POST   | `/api/vehicles`                   | User        | Create a vehicle                     |
| GET    | `/api/vehicles/:id`                | User        | Get one vehicle                      |
| PUT    | `/api/vehicles/:id`                | User        | Update a vehicle                     |
| DELETE | `/api/vehicles/:id`                | **Admin**   | Delete a vehicle                     |
| POST   | `/api/vehicles/:id/purchase`       | User        | Body: `{ amount? }` (default 1). Decrements quantity, rejects if insufficient stock |
| POST   | `/api/vehicles/:id/restock`        | **Admin**   | Body: `{ amount }`. Increments quantity |

## My AI Usage

**Tool used:** Claude (Anthropic), used conversationally as an agentic
coding assistant with direct access to a sandboxed shell, file system, and
the ability to run servers/tests — not copy-paste-from-a-chat-window usage.

**How it was used:**

- **Scoping the work.** Before writing any code, the assistant asked two
  clarifying questions (build scope: full-stack vs. backend-only vs.
  frontend-only; language/framework choice) via a quick option-select
  rather than guessing.
- **TDD workflow, enforced end-to-end.** For every backend module (database
  schema, JWT utilities, auth service, vehicle service, HTTP routes), the
  assistant wrote the test file first, ran it to confirm a genuine failure
  (a compiler error counts, not just an assertion failure), committed that
  as a RED commit, then implemented the minimum code to pass, re-ran the
  suite, and committed as GREEN. This is visible directly in `git log`
  rather than asserted after the fact.
- **Debugging real tooling issues.** The assistant hit and fixed several
  environment problems live: `ts-jest` incompatibility with a just-released
  TypeScript major version (pinned to 5.6.3), an npm peer-dependency
  conflict on `cross-env`, a Tailwind v4 `@import` ordering warning, and a
  `tsconfig` `rootDir` bug that put the compiled server at the wrong path
  for `npm start`. After initial delivery, a user hit `node-gyp`/Visual
  Studio Build Tools failures installing `better-sqlite3` on Windows; the
  assistant migrated the whole data layer to Node's built-in `node:sqlite`
  module instead (same `.prepare().run()/.get()/.all()` API surface, so the
  change was mostly type-import updates), removing the native-compilation
  dependency entirely and re-verified all 36 tests plus a live server smoke
  test afterward.
- **Design decisions, not just code.** For the frontend, the assistant
  produced a short design brief (palette, type pairing, a signature visual
  element — see the Design section above) before writing any component
  code, specifically to avoid the generic "AI dashboard" look, then
  self-corrected mid-build (fixed the same `@import` ordering issue caught
  by the production build).
- **Smoke testing.** Beyond the automated suite, the assistant started the
  compiled backend and the Vite frontend as real background processes and
  exercised the full flow (register → login → create vehicle → list →
  search → purchase → restock → delete, plus the frontend's `/api` proxy)
  with live `curl` requests before considering any layer "done."
- **What it could not do.** The sandboxed environment had no working
  headless browser and no reachable CDN to download one, so the assistant
  could not capture real screenshots — it said so directly rather than
  fabricating a description of what the UI "would look like," and left
  clear instructions for a human to capture them after running the app
  locally.

**Reflection:** The main value of using an AI agent this way over
copy-paste-based AI usage was that it collapsed the write → run → observe
failure → fix loop into a single conversation, which is exactly the loop
TDD asks for — the RED commits in this repo are real compiler/assertion
failures the assistant saw and reacted to, not test files retrofitted to
match already-passing code. The main risk to watch for with this workflow
is the same risk as with any AI-assisted code: an agent that can execute
code and declare success needs to be checked that "tests pass" actually
means the tests assert something meaningful (e.g., the 403-vs-401,
409-vs-400 status code distinctions here were deliberate design choices
that a shallower test suite could have missed entirely). A human reviewing
this repo should read the actual assertions in `backend/tests/`, not just
trust the green checkmark.
